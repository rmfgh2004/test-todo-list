# 타임테이블 기반 투두 리스트 요구사항

## 1. 의도 분석

- **요청 유형**: Greenfield 풀스택 신규 프로젝트
- **범위**: React SPA, Java REST API, H2 영속화와 양측 테스트를 포함한 다중 컴포넌트
- **복잡도**: 중간 이상. 드래그 상호작용, 시간 충돌, 반응형 UX, 데이터 무결성과 보안 게이트 포함
- **대상 사용자**: 인증 없이 로컬에서 사용하는 개인 지식 근로자
- **제품 목표**: 미배치 할 일을 실제 주간 시간에 배치하고 충돌을 명시적으로 해결하는 실행 가능한 계획 도구

## 2. 기능 요구사항

### FR-001 주간 타임테이블 조회

사용자는 월요일부터 일요일까지의 주간 타임테이블을 08:00~22:00 범위와 15분
간격으로 조회한다.

**수용 기준**

- 주간 범위와 각 날짜가 표시된다.
- 배치된 할 일은 시작·종료 위치와 길이에 맞게 표시된다.
- 오늘과 업무일·주말이 시각적으로 구분되며 정보가 색상에만 의존하지 않는다.
- 로딩, 빈 상태, 오류 상태가 각각 명확하다.

### FR-002 주간 탐색

사용자는 이전 주, 다음 주, 오늘로 이동한다.

**수용 기준**

- 이동 후 해당 주의 일정과 미배치 할 일을 다시 조회한다.
- 브라우저 새로고침 후 URL의 주간 기준 날짜로 동일한 화면을 복원한다.

### FR-003 할 일 생성

사용자는 제목, 설명, 우선순위, 예상 소요 시간과 선택적 마감일을 입력해 할 일을 만든다.

**수용 기준**

- 제목은 필수이며 1~120자, 설명은 최대 2,000자다.
- 예상 소요 시간은 15분 단위이며 15~840분 범위다.
- 우선순위는 LOW, MEDIUM, HIGH allowlist만 허용한다.
- 생성 직후 미배치 백로그와 목록 보기에 나타난다.

### FR-004 할 일 조회·수정·삭제

사용자는 할 일 상세를 열고 내용을 수정하거나 삭제한다.

**수용 기준**

- 수정에는 FR-003의 검증 규칙이 동일하게 적용된다.
- 삭제 전 확인을 받고 삭제 후 목록과 타임테이블에서 제거한다.
- 존재하지 않는 ID는 내부 정보를 노출하지 않는 404 응답을 반환한다.

### FR-005 미배치 백로그

아직 시간이 정해지지 않은 미완료 할 일을 주간 화면의 백로그에서 확인한다.

**수용 기준**

- 카드에 제목, 우선순위, 예상 소요 시간과 마감일을 표시한다.
- 우선순위와 마감 임박도를 사용해 안정적으로 정렬한다.
- 배치 완료된 할 일은 백로그에서 제거되고 배치를 해제하면 다시 나타난다.

### FR-006 할 일 시간 배치 및 재배치

사용자는 백로그 카드를 타임테이블로 드래그하거나 날짜·시작 시간을 입력해 배치하고,
이미 배치된 항목을 다른 시간으로 이동한다.

**수용 기준**

- 시작 시각과 예상 소요 시간으로 종료 시각을 계산한다.
- 모든 시각은 Asia/Seoul 정책과 15분 경계에 맞아야 한다.
- 키보드 사용자는 드래그 없이 동일한 결과를 만들 수 있다.
- 저장 성공 전 낙관적 표시를 하더라도 실패 시 이전 상태로 복원하고 오류를 알린다.

### FR-007 시간 충돌 탐지 및 해결

새 배치 또는 재배치가 기존 미완료 일정과 겹치면 저장 전에 충돌을 탐지하고 사용자에게
해결 방법을 요청한다.

**수용 기준**

- 두 반개구간 `[start, end)`이 겹칠 때만 충돌로 판정하며 경계가 맞닿는 경우는 허용한다.
- 충돌 화면에 기존 일정과 제안 일정의 날짜·시간을 표시한다.
- 사용자는 기존 일정 유지, 새 일정을 충돌하지 않는 다음 15분 슬롯으로 이동, 취소 중 선택한다.
- 아무 선택 없이 기존 데이터를 덮어쓰지 않는다.
- 서버가 최종 충돌 판정을 트랜잭션 안에서 다시 수행한다.

### FR-008 배치 해제

사용자는 배치된 할 일을 미배치 상태로 되돌린다.

**수용 기준**

- 시간 정보만 제거하고 제목, 우선순위, 기간과 마감일은 유지한다.
- 작업은 다시 백로그에 나타난다.

### FR-009 완료 상태 관리

사용자는 할 일을 완료하거나 완료 취소한다.

**수용 기준**

- 완료 상태는 목록과 타임테이블에 일관되게 반영된다.
- 완료한 할 일은 기본 백로그에서 제외되지만 목록 필터로 조회할 수 있다.
- 반복 호출에도 최종 상태가 동일한 idempotent 동작을 제공한다.

### FR-010 목록 보기

사용자는 모든 할 일을 목록에서 확인하고 상태, 배치 여부와 우선순위로 필터링한다.

**수용 기준**

- 각 행에 제목, 우선순위, 예상 시간, 마감일, 배치 시간과 완료 상태를 표시한다.
- 정렬과 필터 상태는 URL query로 유지한다.
- 빈 결과와 전체 빈 상태를 구분한다.

### FR-011 반응형 사용자 흐름

핵심 기능은 데스크톱과 모바일에서 완결된 흐름으로 동작한다.

**수용 기준**

- 데스크톱은 백로그와 주간 그리드를 동시에 제공한다.
- 모바일은 날짜 선택과 단일 일 타임라인, 별도 백로그 패널로 재구성한다.
- 320px 너비에서 가로 잘림이나 텍스트 겹침 없이 주요 명령을 사용할 수 있다.
- 모달 열림 시 초점이 갇히고 닫힌 뒤 시작 요소로 복원된다.

### FR-012 데이터 영속화

개발 실행에서는 할 일과 일정이 암호화된 H2 파일 DB에 저장되고 재시작 후 복원된다.

**수용 기준**

- DB 경로와 암호화 키는 외부 설정으로 주입한다.
- 테스트는 각 실행마다 격리된 인메모리 H2를 사용한다.
- Flyway가 스키마 버전을 관리하며 H2 콘솔은 비활성화한다.

### FR-013 변경 감사

생성, 수정, 삭제, 배치, 배치 해제와 완료 상태 변경에 감사 레코드를 남긴다.

**수용 기준**

- 동작, 리소스 ID, 변경 시각, 로컬 사용자 식별자와 민감정보를 제외한 변경 요약을 기록한다.
- 애플리케이션 API는 감사 레코드를 수정하거나 삭제하지 못한다.

## 3. 비기능 요구사항

### NFR-001 테스트 및 TDD

- 모든 기능은 실패 테스트 → 최소 구현 → 리팩터링 순서를 따른다.
- 프론트 statements/functions/lines 80%, branches 75% 이상을 유지한다.
- 백엔드 line/branch 80%, 시간 충돌 도메인 branch 90% 이상을 유지한다.
- 단위, 컴포넌트, API 통합, DB 통합과 데스크톱·모바일 E2E 테스트를 포함한다.
- 테스트 이름과 구현 문서에 관련 `FR-XXX`를 포함한다.

### NFR-002 속성 기반 테스트

- 부분 모드로 PBT-02, PBT-03, PBT-07, PBT-08, PBT-09를 차단 규칙으로 적용한다.
- 시간 parse/format round-trip, 15분 정렬, 종료 시각, 충돌 대칭성·경계 불변식을 검증한다.
- Java는 jqwik, TypeScript는 fast-check를 사용하고 도메인 generator와 seed 재현을 제공한다.
- PBT는 예제 기반 핵심 시나리오 테스트를 대체하지 않는다.

### NFR-003 보안

- Security Baseline SECURITY-01~15를 적용 가능한 범위에서 차단 조건으로 사용한다.
- 모든 코드 변경 묶음은 `aidlc-inputs/04-security-review-checklist.md` 검토를 통과해야 한다.
- H2 파일은 AES 암호화하고 키와 DB 파일을 저장소에 포함하지 않는다.
- 모든 API 입력과 요청 크기를 검증하고 SQL은 JPA parameter binding만 사용한다.
- API는 loopback origin allowlist, rate limit, 안전한 전역 오류 처리와 request ID를 적용한다.
- 웹 보안 헤더를 설정하며 HTTPS 프로필에서 HSTS를 활성화한다.
- lockfile, 의존성 취약점 검사와 CycloneDX SBOM 생성을 CI에 포함한다.

### NFR-004 접근성

- WCAG 2.2 AA 수준의 키보드 조작, 초점 표시, 의미 구조와 대비를 목표로 한다.
- 드래그는 키보드·폼 기반 대체 수단을 제공하고 상태 변경은 `aria-live`로 알린다.
- 색상만으로 우선순위, 오늘, 충돌과 완료 상태를 전달하지 않는다.

### NFR-005 성능

- 로컬 데이터 1,000건에서 일반 API p95 응답 300ms 이하를 목표로 한다.
- 최초 화면은 개발 기준 머신에서 2초 이내 상호작용 가능해야 한다.
- 주간 API는 기간 조건을 필수화하고 목록은 페이지 크기 상한을 둔다.

### NFR-006 데이터 무결성

- 충돌 판정과 저장은 하나의 트랜잭션에서 수행한다.
- API 경계의 날짜·시간은 ISO-8601을 사용하고 내부 정책은 Asia/Seoul로 고정한다.
- 예상 시간과 배치 시간은 15분 배수 불변식을 유지한다.
- DB 예외 발생 시 부분 변경 없이 롤백한다.

### NFR-007 유지보수성

- 프론트와 백엔드는 독립 빌드 단위이며 도메인 경계를 따른다.
- 백엔드 domain은 Spring/JPA에 의존하지 않는다.
- TypeScript strict mode, Java 컴파일 경고, lint와 format을 CI에서 강제한다.
- OpenAPI 계약과 프론트 API 타입의 불일치를 자동 검출한다.

### NFR-008 관측성과 안전한 오류 처리

- 백엔드 구조화 로그에 timestamp, level, request ID, message를 포함한다.
- 사용자 응답에는 내부 예외, 경로, SQL과 스택 트레이스를 노출하지 않는다.
- 프론트 오류 상태는 재시도와 request ID를 제공한다.
- health endpoint로 애플리케이션과 DB 준비 상태를 확인한다.

## 4. API 경계

- 기본 경로: `/api/v1/tasks`, `/api/v1/schedule`, `/api/v1/health`.
- 요청·응답은 JSON이며 `Content-Type`을 엄격히 검증한다.
- 목록은 기간, 상태, 배치 여부, 우선순위 필터와 페이지 크기 상한을 제공한다.
- 오류는 `code`, `message`, `requestId`, `fieldErrors`의 안전한 구조를 사용한다.
- 충돌은 일반 500이 아니라 충돌 상세와 가능한 해결을 담은 409로 반환한다.
